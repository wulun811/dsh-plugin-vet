# 演进纪律（GOVERNANCE）

七个语义对象不是一次设计的结果，而是**一条长期纪律的产物**。这个文件把那条纪律写下来，否则一年后
又会回到"每加一个功能加一个 kind"。

四节对应专家稿的四条要求：新增功能怎么进（§7.3）、什么时候必须停下（§13.2）、谁能断言什么（§3.2）、
以及内容/规则/策略三条失效路径为什么必须互不牵连（§3.3）。

---

## 1. 新增功能的准入流程（§7.3）

任何新的检测能力、新的插件形态、新的开关，**按顺序**走这四步。跳过任何一步的 PR 都该被打回。

1. **真实攻击面**：写下这个能力要挡的真实事件（谁、在什么边界、做了什么、后果是什么）。写不出来就是
   "我觉得应该监控"——那不是攻击面。
2. **已有语义映射**：先试着用现有七类对象表达它。绝大多数新需求在这一步就结束了：
   - 一次观测 → `Evidence`（`code` 必须命中 `domain/kinds.ts` 注册表；不命中说明你其实在发明新语义）；
   - 对观测的判读 → `Assessment`（severity 在判读上，不在 code 上）；
   - "我们看不见这一面" → `CoverageEntry`（`unknown`/`partial`/`excluded`/`unsupported`，不是一条黄牌）；
   - "这个主体是否允许加载" → `Qualification`；
   - "按策略该做什么" → `Decision`；
   - "边界上实际发生了什么" → `Receipt`。
3. **最小不可表达反例**：如果第 2 步映射不了，给出**最小**的反例——一条现有对象表达不了的具体事实，
   并说明为什么"加个 kind"、"加个布尔"不行。这一步是整个流程的核心：它把"我想加个东西"变成了
   "现有模型有一个已知缺口"。
4. **才允许新增对象**。新增对象要同时改：`domain/types.ts`（形状）、`domain/validate.ts`（运行时校验，
   含跨字段契约）、`docs/ARCHITECTURE.md`（它回答什么问题、不回答什么）、以及一条能把"没有它时是错的"
   钉住的测试。四样缺一，这个对象在半年内会退化成注释。

**反例（这些都是真实发生过的）**：`esm-guard-coverage` 曾经是一个 kind，但它描述的从来不是事件，而是
"某个主体的某个面看不全"——0.5.3 把它搬进 `CoverageEntry`，顺带删掉了一个持久化存储、一个会话表和一个
去重定时器（约 160 行只为让一条黄牌不重复）。**凡是需要去重才能不烦人的东西，多半不是事件。**

## 2. 六条停止规则（§13.2）

碰到下面任何一条，**停下来重新设计**，不要靠加特例绕过去。

| # | 停止规则 | 在本仓库里长什么样 | 撞上时先看哪里 |
|---|---|---|---|
| S1 | 候选语义需要越来越多特殊 case 才能表达旧功能 | 同一类报警要三种不同形状才能表达；注册表里出现"仅当 X 时"的分支 | `domain/kinds.ts` 的 `from-site` 行 —— 它们越多，说明模型越没吸收事实 |
| S2 | 新策略无法复现旧档位，且给不出明确的授权性破坏变更 | 改 `PROFILE_PRESETS` 让某个场景从"报警"变成"拦截"，却说不清谁授权了 | `config.ts` 的三条纪律 + `test/config-profile.test.ts` |
| S3 | 关键测试只能凭日志文案认定"已阻止"，无法观察真实副作用 | 断言 `message` 里出现"已拦截"，却没有 oracle 计数 | `domain/receipt.ts` 的三条守卫；`guard/receipt-oracle.ts` |
| S4 | 试图用同进程 Hook 声称 OS 级隔离 | README / 提示文案里出现"隔离"、"沙箱"、"无法绕过"而实现是 T2 | `README*.md` 的信任边界 + `SECURITY.md` |
| S5 | 把插件自己写的报告当成不可伪造的审计收据 | 用插件自述、`vet.contract.json` 或 agent 的解释来提升资格 | `domain/receipt.ts` 的注释：只有世界能证伪的陈述才算收据 |
| S6 | 指标全是行数/依赖量/文档数，而不是受保护边界、攻击回归、误报与证据可信度 | 汇报里出现"新增 1200 行"却没有一条新的反例测试 | `docs/FAILURES.md`（每条都要有"现在由什么挡住"） |

S4 在 0.5.12 真的被撞上过一次：README 写的是"静态层与插件代码**物理隔离**"，而实现是一个同用户、
同机器的子进程。修的不是实现，是那句话（见 `docs/FAILURES.md` F11）。

## 3. 权威矩阵（§3.2）

`Evidence.source` 的七个取值就是七种权威。表里每一行说清**这种来源能断言什么、不能断言什么**，
`Assessment`/`Qualification` 的字段合法性应当由它推导，而不是随手定。

| `TrustOrigin` | 谁 | 能断言 | **不能**断言 | 落到 |
|---|---|---|---|---|
| `local_scan` | 确定性静态扫描 | 这些字节里有这些模式；规则可复现、输入可哈希 | 代码会不会被调用；运行时行为；"安全" | `verdict` / `staticScore` / `findings` |
| `runtime_hook` | 同进程 T2 钩子 | 被包裹的 API 上发生过这次调用（含参数形状） | 越过 ESM 具名导入 / `process.binding` / 原生插件的调用；调用者的真实意图 | `n1`/`n3` 系列 `Evidence` |
| `sidecar` | T1 哨兵（独立进程） | 宿主进程树的内存/fork/fd 采样值 | 把某个资源事件归因到某个插件（通常做不到） | `sentinel` / 内存类 `Evidence` |
| `external_advisory` | OSV / registry | 某个 `name@version` 有公告；某个名字与热门包相似 | 本机装的就是这个字节；运行时暴露面 | `rule: 'OSV'` finding、typosquat |
| `plugin_claim` | 插件自述（`vet.contract.json` 等） | 插件**声称**自己要什么 | 它实际做了什么；任何资格的提升 | M1 契约（记录档，永不压制既有报警） |
| `agent_review` | 人/agent 按协议审阅 | 静态判据之外的人工判断与理由 | 覆盖确定性判据；把"审过了"变成"运行期安全" | 健康档案正文（`subject_sha256` 绑字节） |
| `human_attestation` | 部署者的显式动作 | 认可某个哈希、放行某个包、改档位 | 改变事实；外溢到其他对象 | `acknowledgedPackageHashes`、allowlist、档位 |

**读法**：一条结论的可信度等于它**最弱的**那个来源，而不是最高的。`plugin_claim` 与 `local_scan` 冲突时，
事实以 `local_scan` 为准、意图以 `plugin_claim` 为准，两者都不是"谁赢"，而是回答不同的问题。

## 4. 三条失效轴互不牵连（§3.3）

内容变、规则变、策略变是**三条独立的路径**，各自的处置不同：

| 轴 | 触发 | 处置 | 禁止 |
|---|---|---|---|
| **内容变**（同版本不同字节 / 版本变了） | `subject_sha256` 对不上、基线不一致、TOCTOU 快照漂移 | `QUALIFIED → RECHECK_REQUIRED`（`content_changed`） | 拿"名字和版本没变"当没变 |
| **规则变**（静态规则集版本变了） | `Assessment.ruleSetVersion` 与当前引擎不符 | 只有**这条规则会在本主体上得出不同判定**时才 `RECHECK_REQUIRED`（`standard_changed{impacts}`） | "任何字段变了就全清"——那是大规模误拒载的配方 |
| **策略变**（档位 / 守卫 / 门槛） | `profile`、`runtimeGuard`、`confirmBlock`、`denyOn` 改动 | **不改变任何资格**（`runtime_config_changed` → 原态不变） | 让改配置等于让全部审计作废 |

这两条"禁止"是同一条原则的两面：**失效必须由事实驱动，不能由"有东西变了"驱动。**

今天的落地状态（诚实版）：

- 内容轴：已接（`audit/archive.ts::probeQualification` + 内容基线 + TOCTOU 快照比对）；
- 策略轴：已接（改档位不动资格；`effectiveConfig` 把"设了但没用"的键标出来）；
- 规则轴：**只有状态机的一格，没有生产者**。档案格式里没有 `rule_set_version`，所以 `standard_changed`
  在生产里触发不了。补它需要三件事一起做（档案写版本 + 判定、加载时做影响函数、只在会得出不同判定时才转
  `recheck_required`），否则就是 S2 那类"没有授权的破坏性变更"。`test/assessment-freshness.test.ts`
  把这个缺口钉成了断言。

## 5. 怎么用这份文件

- 提 PR 加能力：先对第 1 节的四步，把答案贴在 PR 描述里。
- 做取舍时心里打鼓：对第 2 节的六条，撞上哪条就写哪条。
- 新写一条断言"来源可信"的代码：先查第 3 节，`source` 的取值必须来自那七行。
- 处理"过期/失效"：先问是哪条轴，再查第 4 节那两列"禁止"。
